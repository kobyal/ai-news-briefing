ב-10 באפריל 2026 מישהו העלה ל-imgur צילום מסך עם טענה שאנטרופיק מזריקה `reasoning_effort=25` ל-system prompt של Claude.ai. 206 צפיות, לא בדיוק סערה, ולא בדקתי אם זה נכון. אבל זה מזכיר משהו שהרבה צוותים מפספסים: מה שאתם מקבלים ב-claude.ai הוא לא המודל לבד. זה המודל ועוד system prompt שאנטרופיק כותבת ומעדכנת. בדף ה-release notes שלהם, בגרסה מ-16 באוגוסט 2026, זה כתוב במפורש:

> "These system prompt updates do not apply to the Claude API."
> — אנטרופיק, Release notes: System prompts

בקיצור, ב-API אף אחד לא כתב בשבילכם system prompt. את ה-role של `system` הכניסה OpenAI ל-chat API במרץ 2023, ומאז כולם עובדים עם אותה תבנית. בחלק הקודם ראינו שפורמט, context ו-retry עוברים ל-harness. הפעם נעבור על מה שכן נשאר בתוך ה-system prompt, באיזה סדר, וכמה זה עולה. שישה צעדים, כולם מה-pipeline שלנו.

## 01 · להריץ את אותה שאלה פעמיים

לפני שכותבים מילה, תבדקו מה המודל עושה בלי ההוראות שלכם. ניסיתי את זה עם `claude -p`, ויש כאן מלכודת קטנה. `claude -p` בלי דגלים לא רץ בלי system prompt. הוא רץ עם ה-system prompt של Claude Code עצמו. `--system-prompt` מחליף אותו, `--append-system-prompt` מוסיף עליו. אם ה-agent שלכם לא כותב קוד, ההבדל הזה חשוב, כי אתם יורשים התנהגות של כלי קוד בלי לדעת.

```bash title="ab_system.sh"
Q='סכם בשורה אחת למהנדסים: אנטרופיק הוסיפה TTL של שעה ל-prompt caching.'
claude -p "$Q" > default.txt
claude -p --system-prompt "$(cat prompts/editor_system.md)" "$Q" > ours.txt
diff default.txt ours.txt
```

מה תראו: בריצה הראשונה המודל מחליט לבד על אורך, טון ופורמט. בשנייה, עם הקובץ שנבנה בצעד הבא, יוצא אובייקט עם שני שדות שאפשר להעביר ל-`json.loads`. בשורה התחתונה, זה כל מה ש-system prompt עושה: מחליף את הדיפולטים של המודל בדיפולטים שלכם. תשמרו את `default.txt`. זה ה-baseline שלכם.

## 02 · ארבעה בלוקים, תמיד באותו סדר

אצלנו כל system prompt בנוי מאותם ארבעה חלקים: role, rules, examples, output contract. ה-role הוא שתיים-שלוש שורות, לא "אתה מומחה עולמי". מי אתה, למי אתה כותב, מה נחשב הצלחה. ה-rules הם גבולות: מה אסור, מה חובה, מה עושים כשחסר מידע. ה-examples הם זוגות. ה-output contract הוא הסכמה, בדיוק כמו שהקוד יבדוק אותה.

```markdown title="prompts/editor_system.md"
<role>
עורך חדשות AI. כותב למהנדסים ישראלים.
הצלחה = כותרת שמהנדס היה שולח לקבוצה של הצוות.
</role>
<rules>
- רק מה שכתוב בקלט. חסר מידע? שדה ריק, לא ניחוש.
- בלי סופרלטיבים, בלי emoji.
</rules>
<examples>
<bad>אנטרופיק משיקה יכולת פורצת דרך לחיסכון בעלויות</bad>
<good>אנטרופיק: cache של שעה במקום 5 דקות</good>
</examples>
<output_contract>
JSON בלבד: {"headline": "עד 12 מילים", "why_it_matters": "עד 25 מילים"}
</output_contract>
```

הסדר לא אסתטי. מה שיציב למעלה, מה שמשתנה למטה. ה-role וה-rules כמעט לא זזים בין ריצות. ה-contract זז כשמשנים schema. והקלט של היום לא נכנס לשם בכלל, הוא הולך ל-user message. ל-merger שלנו נכנסים כל בוקר כמה עשרות stories מעשרה agents, וה-system prompt שלו לא מכיר אף אחד מהם. הוא מכיר רק את הכללים. תזכרו את זה לצעד 06, שם זה הופך לכסף.

## 03 · XML לגבולות, markdown בתוך הבלוק

הוויכוח הזה נמשך שנתיים, ובגדול הוא מיותר. אנטרופיק ממליצה על XML tags במדריך ה-prompting שלה, והסיבה פרקטית: תג סגור אומר למודל בדיוק איפה דבר אחד נגמר ואיפה השני מתחיל. markdown נוח להוראות שבן אדם עורך. אצלנו הכלל פשוט. תג לכל גבול: בין בלוקים, ובעיקר סביב כל מה שבא מבחוץ. בתוך בלוק, markdown רגיל.

רגע, למה זה משנה בפועל? כי טקסט מבחוץ מכיל הוראות. כתבה שמצטטת prompt, README עם "ignore previous instructions", או Jina שמחזיר `![Image](url)` באמצע הטקסט. בתוך `<article>` המודל מבין שזה חומר גלם. בלי התג, זה נראה כמו עוד שורה ב-rules.

## 04 · few-shot: זוג אחד רע, זוג אחד טוב

zero-shot עובד מצוין כשהמשימה ברורה והפורמט סטנדרטי. סיווג ל-vendor, למשל, אצלנו בכלל לא צריך מודל. יש `classify_vendor` עם כללים. few-shot נכנס כשהמשימה היא "תכתוב כמו X" וקשה להגדיר את X במילים.

המקרה הכי ברור אצלנו הוא התרגום לעברית. ניסינו לתאר במילים "עברית טבעית, לא מתורגמת". לא עזר. מה שעזר זה זוגות BAD/GOOD בתוך ה-system prompt של התרגום: משפט שנשמע כמו מכונה, ולידו איך מהנדס היה אומר אותו. זה המנוף הכי חזק שמצאנו, יותר מכל הנחיה.

> **הדעה שלי:** זוג BAD/GOOD אחד שווה יותר מפסקה של הגדרות סגנון. המודל לא מבין "טבעי", הוא מבין דוגמה. אני כבר לא כותב הנחיית סגנון בלי זוג לצידה.

מה שכן, דוגמאות הן גם סיכון. המודל מעתיק אותן, כולל אורך, מבנה ולפעמים מילים ספציפיות. שתיים-שלוש דוגמאות ששונות זו מזו עדיפות על חמש שנראות אותו דבר. ואם כל הדוגמאות שלכם על אנטרופיק, תקבלו כותרות שמזכירות את אנטרופיק גם כשהכתבה על גוגל.

## 05 · כמה ארוך זה יותר מדי

אין מספר tokens קסום. ה-system prompt של ה-agent שכותב את הבלוג הזה ארוך, וזה בסדר, כי כל סעיף בו נולד מפוסט שיצא רע. השאלה היא לא כמה מילים, אלא שלוש שאלות על כל כלל:

1. אפשר לבדוק את זה בקוד? "JSON בלבד", "עד 160 תווים", "בלי emoji". את כל אלה validator תופס בחינם. אז הקוד אוכף, וה-prompt רק מזכיר בשורה.
2. הוא סותר כלל אחר? שני כללים שמושכים לכיוונים הפוכים, והמודל בוחר ביניהם כמעט באקראי.
3. מה קורה אם מוחקים אותו? אם אין לכם דרך לענות, אין לכם eval. על זה בחלק 3.

בגדול, prompt מתנפח כשכל באג נפתר בעוד שורה. אצלנו כל מקום שבו החלפנו הוראה למודל בכלל בקוד יצא זול ואמין יותר. ה-wrapper של `claude -p` מתקן JSON שבור, ולכן ה-output contract ב-prompt קצר והאכיפה יושבת בקוד.

## 06 · prompt caching: הסדר הוא הכסף

עכשיו לחשבון. prompt caching של אנטרופיק שומר prefix של ה-prompt עד breakpoint שמסמנים עם `cache_control`. ברירת מחדל 5 דקות, אפשרות לשעה, וכל פגיעה ב-cache מרעננת אותו בלי עלות. בטבלת התמחור כתיבה ל-cache של 5 דקות היא פי 1.25 ממחיר קלט רגיל, וקריאה ממנו היא בערך עשירית.

ופה הסדר מצעד 02 מחזיר את עצמו. ה-cache עובד על prefix מדויק. שינוי של תו אחד למעלה, וכל מה שמתחתיו נכתב מחדש. הטעות הכי נפוצה שראיתי: תאריך היום בשורה הראשונה של ה-system prompt. נשמע הגיוני, שובר את ה-cache בכל ריצה. התאריך הולך ל-user message.

עוד פרט מהדוקס ששווה להכיר: ה-TTL נמדד מתחילת הבקשה, לא מסוף התשובה. אם תשובה לוקחת 4 דקות לזרום, נשארת לכם בערך דקה להתחיל את הבקשה הבאה לפני שה-cache של 5 דקות פג. ב-pipeline שכותב תשובות ארוכות, ככה מפספסים cache בלי לשים לב. אם יש לכם agents שרצים אחד אחרי השני על אותו system prompt, תשקלו TTL של שעה.

```python title="cached_system.py"
import anthropic

client = anthropic.Anthropic()
SYSTEM = open("prompts/editor_system.md", encoding="utf-8").read()

def run(user_text: str):
    resp = client.messages.create(
        model="claude-sonnet-5-5",
        max_tokens=1024,
        system=[{
            "type": "text",
            "text": SYSTEM,
            "cache_control": {"type": "ephemeral", "ttl": "1h"},
        }],
        messages=[{"role": "user", "content": user_text}],
    )
    u = resp.usage
    print("write:", u.cache_creation_input_tokens, "read:", u.cache_read_input_tokens)
    return resp
```

תריצו פעמיים ותסתכלו על `read` בקריאה השנייה. אם הוא אפס, משהו ב-prefix זז. ויש מינימום אורך ל-prefix שנכנס ל-cache, תלוי מודל, וה-skeleton מצעד 02 קצר ממנו. כלומר זה משתלם כשה-system prompt ארוך באמת, בדרך כלל בגלל הדוגמאות. אצלנו הכתיבה הכבדה רצה על subscription, אז החשבון הזה פחות כואב לנו. מי שמשלם API לפי token, זה ההבדל בין מספר שאף אחד לא מסתכל עליו לבין שורה בחשבון החודשי.

## מה לקחת

- לפני שכותבים system prompt, להריץ בלי ולשמור את הפלט כ-baseline.
- role, rules, examples, contract, בסדר הזה. כל מה שמשתנה, כולל התאריך, ב-user message.
- כל טקסט שבא מבחוץ נכנס בתוך תג. ההוראות שלכם ב-markdown.
- כלל שאפשר לבדוק בקוד, נבדק בקוד. ה-prompt רק מזכיר אותו.
