There's a developer in Italy who runs a RAG app for pension and tax advisors. People ask it about INPS, about pension funds for self-employed professionals, about laws and regulations. It answers from documents uploaded to a knowledge base.

For a long time it was classic RAG. Take the question, search the DB, push the results into the system prompt, call the model once. It works until the first search misses. Then the answer is bad, and the model can't do anything about it. Retrieval happened before the model even got to think about the question.

So he rebuilt it as an agent, in plain Ruby, and wrote about it in June. That's more or less the whole story of agentic RAG.

## The model drives the search

The one-line definition: instead of your code searching and then handing results to the model, the model runs the search itself. It decides what to search for, reads what came back, searches again with different words, follows references between documents, and only then writes an answer.

RAG itself came from a 2020 Facebook AI Research paper. The "agentic" part didn't come from any single paper. Nobody invented it. It just stuck once everyone started giving models tools. IBM has an explainer page for it now.

What it isn't: it isn't "RAG with LangChain". The Italian version runs on Rails and RubyLLM, with no LangChain and no Python on the side. It also doesn't have to be multi-agent. One agent, a few tools, a loop. That's it.

Machine Learning Mastery gives an example that shows why you'd want this: "Compare Q3 2025 sales to Q1 2026 and summarize the risk factors from the latest SEC filing." Plain RAG embeds that whole mix and returns chunks that look like the average of three different questions. In other words, like none of them. An agent splits it into three searches, sends each one to the right source, and checks what came back.

## Three tools and a loop

The nice thing about panasiti's post is how little changed. Same pgvector through the neighbor gem, same pg_search with an Italian dictionary, same chunks. What moved: the search no longer runs before the model. The model gets three tools:

- `search_knowledge_base`: the same search as before, except now the model presses the button
- `fetch_document_section`: pull a section from a document when a chunk is cut off
- `list_documents`: see what's in the knowledge base at all

The model calls them as many times as it needs. When it has enough material, it writes an answer with citations. Everything runs in a background job, and the agent's steps stream to the browser over Turbo Streams. The user sees what it's searching for in real time.

MLM breaks this into three moves: query decomposition, multi-hop chaining, self-correction. In standup terms: split the question, follow a lead, and admit when you missed and search again.

## Ten nodes, mostly guardrails

In August a project called "11-Node Agentic RAG with MCP and PII Shield Under 512MB RAM" showed up on HN. The page itself says 10-Node LangGraph. We won't argue over a node.

The system answers questions about the Indian constitution, state budgets and tax law. Look at what each node does:

- Classifier sorts intent: RAG question, greeting, abusive, vague, out of scope
- CrossQuestioner asks a clarifying question when the query is vague, two rounds max
- Retriever pulls from Pinecone, and a Cohere reranker keeps 10 chunks out of 100+ candidates
- Hallucination Guard checks after writing that the answer is grounded in what was retrieved, and rejects it below 40% confidence
- Fallback with a circuit breaker: three API failures and the circuit opens, no crash and no hang

There's also web search through Tavily that only runs after human approval, and a one-hour Redis cache.

Wait, where's the agentic part? In the retriever, in tool calling for stock prices, in the decision to go to the web. Everything else is guardrails: classification, checks, retry, cache and a brake. And that's exactly what makes it something you can leave running on its own.

## Bayer called it something else

Martin Fowler's site published the story of PRINCE, Bayer's agentic RAG system for preclinical research. The problem: researchers who need to ask complicated questions over huge amounts of internal data, and keyword search with boolean logic that doesn't hold up.

The interesting part isn't the architecture. It's the admission that when they designed the system, they had no names for what they were doing. Today they describe it as context engineering and harness engineering.

Context engineering decided what each model gets, what it doesn't get, and how context moves between stages: research, reflection, writing. Harness engineering is all the scaffolding around it: orchestration, tool limits, state, retries, fallbacks, validation, reflection loops, observability and human review.

Read that list again. It's the same list as the Show HN project, just the pharma version with a paper in Frontiers in AI.

## When to keep plain RAG

MLM admits it too: plain RAG works fine for simple, clear questions. And the cost of the loop is real:

- Every round is another model call, more tokens, more latency
- The number of steps varies per question, so do the bill and the response time
- Evals get harder, because the same question can take a different path on every run
- Without a cap on rounds, an agent that can't find anything will keep searching long after it should have given up

If most of your questions are "where's the form", you don't have an agent problem. You have an FAQ problem.

And us? The daily aibriefing pipeline has about 10 agents, and every place we swapped a model call for a rule got cheaper and more reliable. Our most useful loop isn't smart at all: the `claude -p` wrapper retries transient failures and repairs broken JSON. Boring and good, and it closed three production incidents. Our worst bugs weren't wrong answers, they were silent failures. An agent that searches six times and returns a confident answer based on nothing is exactly that kind of failure.

The agent decides what to search for. You decide when it stops, and who checks it.
