## מאיפה זה הגיע

באנתרופיק השתמשו במילה harness כבר בנובמבר 2025. בפוסט "Effective harnesses for long-running agents" הם קראו ל-Claude Agent SDK "agent harness כללי", והראו איך גרמו לאופוס 4.5 להתקדם לאורך כמה context windows. בגדול יש שם שני agents. initializer agent מכין את הסביבה בהרצה הראשונה, ו-coding agent מתקדם פיצ'ר אחד בכל session ומשאיר artifacts לסשן הבא. רגע, למה זה בכלל בעיה? כי כל session מתחיל בלי זיכרון. כמו משמרת מהנדסים שנכנסת ולא יודעת מה עשתה המשמרת הקודמת.

את harness engineering כשם של תחום, Addy Osmani מייחס ל-Viv Trivedy. Trivedy פרסם ב-X את "Anatomy of an Agent Harness" עם הנוסחה "Agent = Model + Harness. If you're not the model, you're the harness." ובמקביל Birgitta Böckeler כתבה על זה ב-martinfowler.com, ויש מי שנותנים לה את הקרדיט על המונח עצמו. המסמך של Habitat-Thinking, למשל, קושר את זה ישר ל-test harness הקלאסי: טסטים לא הופכים קוד לנכון, הם תופסים את הרגע שהוא הפסיק להיות נכון.

מי שהפכה את זה למילה שכולם זורקים היא OpenAI, עם הפוסט "Harness engineering: Leveraging Codex in an agent-first world". הם בנו מוצר פנימי בלי אף שורת קוד שנכתבה ביד. חמישה חודשים, בערך מיליון שורות, כ-1,500 PRs שנמזגו. שלושה מהנדסים בהתחלה, ממוצע של 3.5 PRs למהנדס ביום. המשפט המרכזי שלהם: "Humans steer. Agents execute." ומשם זה רק התרחב. במרץ 2026 אנתרופיק פרסמה ארכיטקטורה של planner, generator ו-evaluator. ביולי Lilian Weng כתבה על ה-harness כשכבה מרכזית ב-recursive self-improvement. והחודש ב-Marmelab סקרו את התחום דרך 246 repos ו-57 פרסומים.

## מה זה באמת

בגדול, harness engineering זה התכנון של כל מה שעוטף את המודל בתוך agent: ה-prompt וה-AGENTS.md, הכלים, מדיניות ה-context, hooks, sandbox והרשאות, subagents, לולאות בדיקה ומסלולי התאוששות כשמשהו נופל. Lilian Weng נתנה את ההגדרה הכי מסודרת: המערכת שמסביב למודל הבסיס, שקובעת איך הוא מתכנן, קורא לכלים, רואה ומנהל context, שומר artifacts ומעריך תוצאות. Osmani נתן את הגרסה המעשית: כל פעם שה-agent טועה, בונים משהו שלא ייתן לו לטעות ככה שוב.

ומה זה לא. זה לא prompt engineering, ה-prompt הוא רכיב אחד מתוך עשרה. זה גם לא context engineering, שעוסק במה המודל רואה. ה-harness כולל את זה, ומוסיף מה המודל יכול לגעת בו, איך בודקים אותו ומתי מאפסים אותו. וזה לא framework. Agent SDK או LangChain הם חומרי בניין. ה-harness זה מה שאתם בונים מהם בשביל ה-repo והצוות שלכם.

## איך עושים את זה

1. **מפה, לא אנציקלופדיה.** AGENTS.md או CLAUDE.md קצר שמפנה למסמכים. ל-2,000 שורות ה-agent פשוט לא מגיע עד הסוף.
2. **פירוק ו-artifacts בין sessions.** רשימת פיצ'רים ב-JSON, קובץ progress, ו-commit אחרי כל צעד. זה מה שעצר את ה-agent של אנתרופיק מלנסות לבנות את כל האפליקציה בבת אחת ולהיתקע באמצע בלי context.
3. **בדיקה דטרמיניסטית אחרי כל פעולה.** טסטים, lint, schema ו-type-check שרצים דרך hooks. לא "בבקשה תריץ טסטים" בתוך ה-prompt.
4. **evaluator נפרד מה-agent שכותב.** אנתרופיק הפרידו generator מ-evaluator בהשראת GANs. agent שבודק את עצמו נוטה להכריז על ניצחון מוקדם מדי.
5. **כל טעות הופכת לחוק.** ה-agent שבר convention? מעכשיו יש lint rule או בדיקה ב-CI, לא הערה בצ'אט.
6. **הרשאות ו-sandbox.** מחליטים מראש מה ה-agent רשאי למחוק, לדחוף ולעשות לו deploy.
7. **Observability.** לוגים שגם ה-agent וגם בן אדם יכולים לקרוא. בלי זה אתם מדבגים ניחושים.

הדוגמה הכי קצרה לסעיף 3, ב-Claude Code: hook שמריץ טסטים אחרי כל עריכה. exit 2 מחזיר את הכישלון ל-agent.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "npm test --silent || exit 2" }]
      }
    ]
  }
}
```

## מה זה נותן, ומה זה לא

יש בדיוק מספר אחד שנמדד כמו שצריך. מישהו הריץ את אותו מודל דרך 8 harnesses שונים, על אותן 25 משימות, אותו ספק, אותם כלים. שיעור ההצלחה: בין 68% ל-88%. ב-Marmelab, שציטטו את הניסוי, מודים שזה בערך הדבר היחיד שמישהו מדד ברצינות. כל השאר, כולל רוב מה שכתוב כאן, זה ניסיון מהשטח ולא ניסוי מבוקר.

מה זה לא נותן. harness לא הופך את המודל לחכם יותר, כמו שמנסחים את זה בקורס של walkinglabs. הוא נותן לו מערכת עבודה עם לולאה סגורה. וזה לא בחינם, לא בכסף ולא בזמן. כל חוק שהוספתם הוא קוד שצריך לתחזק. החוקים מצטברים, מתנגשים, ובסוף יש לכם harness שאף אחד לא מבין.

ואז יש את build vs buy. Rajit Khanna מ-prismvideos מחק agent שבנה על Vercel AI SDK ועבר ל-Hermes, כי זיכרון, skills ו-automations הגיעו שם מוכנים. ההמלצה שלו: אם מישהו כבר בנה את החלק הגנרי, אל תבנו harness משלכם. תשקיעו בכלים ובידע שרק לכם יש.

## דוגמה מהשטח

אצלנו ב-aibriefing.dev רץ כל בוקר גרף של כעשרה agents עם שלב merger, ואחרי ה-publish רץ QA evaluator שמסמן P0. ה-wrapper שלנו סביב `claude -p` הוא harness קטן לכל דבר: retry לתקלות חולפות, ותיקון JSON שבור לפני שמישהו מנסה לפרסר אותו. ככה נסגרו שלוש תקלות בפרודקשן. לא מודל טוב יותר, לולאה של כמה עשרות שורות. והלקח העיקרי: הבאגים הכי גרועים שלנו לא היו תשובות שגויות. הם היו כשלונות שקטים. run שנגמר "בהצלחה" עם תוצר ריק. בגלל זה ה-wrapper יושב ב-`shared/` ולא מועתק לכל agent. כשהלוגיקה הזאת הייתה מפוזרת בכמה עותקים, תיקנו אחד והשאר נשארו שבורים.
