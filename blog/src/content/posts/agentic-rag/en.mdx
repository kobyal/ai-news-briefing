## Where it came from

The term has no single inventor and no birth date. Classic RAG has been around for a few years. You embed the question, pull the most similar chunks, put them in the prompt and call the model once. "Agentic RAG" started as a name for the version with a loop in it. It spread first through vendor explainer pages. IBM, for example, has a page of its own on it.

In 2026 it moved from marketing to practice. MachineLearningMastery (May 2026) defined it as RAG where an agent breaks the question apart, sends each part to the right source, checks what came back, and keeps going until it has enough grounded context. In June, Panasiti published a post on RubyLLM and Rails. He moved an app for pension and tax advisors in Italy from single-shot to an agent. Around the same time, Bayer described PRINCE on martinfowler.com. It is an agentic RAG system for preclinical research. In August came a Show HN from Ambuj Kumar Tripathi: a LangGraph graph for legal and financial documents in India that runs in under 512MB of RAM. The title says 11 nodes and the page itself says 10, but that matters less.

The problem the name describes is simple, and Panasiti put it well. In classic RAG, retrieval happens once, before the model has had a chance to think about the question. If the first search missed, the answer comes out bad, and the model has no way to fix it.

## What it actually is

Agentic RAG is RAG where the model runs retrieval itself. It doesn't get a ready-made block of context. It gets tools, such as `search_knowledge_base`, `fetch_document_section` and `list_documents`, and calls them in a loop. It searches, reads, rewrites the query and follows references between documents. It writes an answer with citations only once it has enough material. The vectors and the index stay the same. What changes is who decides what goes into the context, and when to stop searching.

What it isn't:

- It isn't "RAG with a better reranker." A reranker improves a single retrieval pass. It doesn't add any decision.
- It isn't GraphRAG. GraphRAG is about how the index is structured, and you can run it without an agent.
- It doesn't have to be multi-agent. Panasiti uses one model with three tools.
- It isn't a general agent with web search. The knowledge base stays at the center. Web search is a fallback, not the default.

Relative to context engineering, agentic RAG is a special case: the model builds its own context. Bayer said this outright. Most of the decisions in PRINCE, they write, can now be understood as context engineering and harness engineering. Nobody was using those terms yet when they designed the system.

## How to do it

1. **Tools, not a blob.** Give the model search, section fetch and a document list. A single "fetch everything" tool puts you back in single-shot.
2. **Hybrid search and rerank.** Panasiti combines pgvector with full-text search in Postgres. The Show HN pulls 100+ candidates, and a Cohere reranker keeps 10.
3. **A router before the loop.** Classify intent first: simple question, ambiguous question, or out of scope. Ambiguous questions get a clarifying question, up to two rounds. Simple questions don't need an agent at all.
4. **Budget and stop conditions.** Set a maximum number of tool calls, a token ceiling, and a clear definition of what counts as "enough."
5. **A grounding check after writing.** Verify that every claim rests on a retrieved chunk. In the Show HN, an answer below 40% confidence is rejected.
6. **Fallback and circuit breaker.** After three API failures the circuit opens, and the user gets a proper message instead of a frozen screen.
7. **Observability for every step.** Log every tool call (they use Langfuse), and stream the steps to the UI, the way Panasiti does with Turbo Streams. Without that, you can't debug a loop.

Here is a minimal contract. The values are only illustrative:

```yaml
tools:
  - search_knowledge_base
  - fetch_document_section
  - list_documents
limits:
  max_tool_calls: 8
  max_context_tokens: 40000
stop_when: every_claim_has_citation
grounding_check:
  required: true
  reject_below: 0.4
fallback: single_shot_answer_with_warning
```

## What it buys you, and what it doesn't

What you get: you can finally answer multi-hop questions. MachineLearningMastery gives a good example: "Compare Q3 2025 sales to Q1 2026 and summarize the risk factors from the latest SEC filing." Single-shot returns a mix of chunks that answers no part of that well. An agent splits it into separate queries. The same goes for comparing versions, like the Show HN comparing a 1961 law to its 2025 version. Most important, the system can recover from a bad first search.

What you pay: latency and tokens grow with every round. The same question can take a different path on each run, so your eval has to check the path too, not just the answer. The loop can also stop too early. It decides it has found enough and returns a confident answer built on half the material.

One more point: most of the work isn't the agent. Bayer lists what the harness includes: orchestration, tool boundaries, state persistence, retries, fallbacks, validation, reflection loops, observability and human review. That is a list of entirely ordinary engineering. If most of your questions are direct fact lookups, single-shot will be cheaper, faster and more predictable.

## From our own pipeline

The daily aibriefing.dev pipeline is not a RAG system. It's a graph of about ten agents with a merger step, and it taught us the lesson that matters most here. Our worst bugs weren't wrong answers. They were silent failures: a step that returns empty or partial output and reports that everything is fine. So we have a QA evaluator that runs after publish and flags P0s. We also have a wrapper around `claude -p` that retries transient errors and repairs broken JSON. That small loop closed three production incidents. Agentic RAG is exactly the same story. A loop that stops after one search because "that looks like enough" is a silent failure, just with citations. Put the checker outside the loop, and don't trust what the model reports about itself.
